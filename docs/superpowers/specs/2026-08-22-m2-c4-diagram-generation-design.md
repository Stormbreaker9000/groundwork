# M2 C4 Diagram Generation — Design

**Ticket:** STO-101
**Date:** 2026-08-22
**Status:** approved

## Problem

The design stage emits components, interfaces and ADRs. It emits no views. A
reader who wants to know the shape of the system reads eleven component files
and twelve interface files and assembles the graph in their head — which is
the same failure mode STO-220 describes for the pipeline itself.

Three slots have been sitting open for this ticket, each declared by a
shipped ticket that deliberately stopped short:

- `skills/design/SKILL.md` — *"This stage does not write C4 diagrams.
  `.sdlc/design/diagrams/` is a declared dispatch slot owned by STO-101."*
- `skills/design/scripts/validate_design.py:91` — `SKIP_DIRNAMES = {"diagrams"}`,
  with the module docstring recording *"skipped — STO-101 owns the format"*.
- `agents/design-orchestrator.md` — Stage 12, *"Not implemented. When STO-101
  lands, this stage receives the component and interface set and returns the
  diagram files it wrote for `traces_to.diagrams` back-population."*

The schema already carries `traces_to.diagrams` as a string array that nothing
populates.

## Evidence

**The graph is already fully described in frontmatter.** Every edge this
ticket needs to draw exists as data today:

- `CMP.depends_on` — the interfaces a component consumes
- `IF.provider` — the component that provides an interface
- `CMP.boundary` — `internal` or `external`, which is exactly C4's system
  boundary

Confirmed against the shipped tamagotchi worked example (`docs/requirements/
examples/tamagotchi/design/`): 11 components — 9 `internal`, 2 `external`
(`CMP-010 OS Notification Service`, `CMP-011 System Clock`) — and 12
interfaces. The context-level system boundary is therefore already computable
with no judgment at all, and so is every relation at component level.

**What the frontmatter does not carry** is exactly two things, and both are C4
concepts with no counterpart in the artifact model:

1. **Containers.** Components are logical units of responsibility. C4
   containers are deployable/runtime units. Nothing in a component spec says
   which container it runs in.
2. **Actors.** `Person()` at context level has no representation in the design
   set. External *systems* do (`boundary: external`), but people do not.

That split is what the whole design turns on: the parts that are derivable are
generated by a script and cannot drift; the two parts that are not are the
only thing an agent is asked for.

## Decisions

### D1 — A script draws, an agent groups

`generate_c4.py` emits all three levels deterministically from CMP/IF
frontmatter. A new `c4-generator` agent supplies only the container grouping
and the actor list.

This matches the split the pipeline already runs on: structure is script-gated
(`validate_design.py`, `validate_traceability.py`), judgment is agent-owned
(the specialists, the critic). It also removes the failure mode an
agent-authored diagram would carry — a diagram that says `CMP-002 → CMP-005`
while the frontmatter says otherwise, with nothing in the pipeline able to see
the disagreement.

Rejected: an agent authoring the Mermaid by hand (drift, and it would need a
consistency linter written anyway); a script with no agent at all (the Context
and Container views would need new schema fields on every component to carry
information the component genuinely does not have).

### D2 — The generator runs at Stage 9.6; the script runs inside the formatter

The orchestrator currently declares this work as Stage 12, *after* the
formatter. That placement is wrong, and it is wrong for a reason the pipeline
has already paid for once.

Stage 11 was retired for exactly this. ADR generation originally sat after the
formatter, and `agents/design-orchestrator.md` records why it moved to Stage
9.5: a post-formatter generator *"would be a second writer: it would re-open
CMP/IF files the formatter had already written and the validator had already
passed, patch `traces_to.adr` into them, and re-run the gate. STO-99 and
STO-215 both landed fixes whose entire point was to make the formatter the
single writer and the single structural gate."*

Diagram generation has the identical shape — it writes files and needs
`traces_to.diagrams` back-filled onto artifacts the formatter already wrote —
so it takes the identical resolution:

```
Stage 9.5   adr-generator      → draft_adrs
Stage 9.6   c4-generator       → draft_diagram_model   (containers, actors)
Stage 10    design-formatter
              writes CMP/IF/ADR files
              → runs generate_c4.py over what it just wrote
              → back-fills traces_to.diagrams
              → validate_design.py   ← ONE gate, over everything
```

The script's primary input is a design directory on disk, so it also re-runs
standalone over any existing set — which is what STO-219 will want, and what
makes the tamagotchi smoke test in D7 possible.

Stage 12 is retired in the orchestrator with a note pointing here, in the same
form Stage 11 already carries.

### D3 — Diagrams are atomic artifacts with `DIA-` IDs

A fourth artifact type, sharing the base schema with components, interfaces
and ADRs:

```yaml
---
id: DIA-003
type: diagram
title: Component View — Desktop App
description: Internal structure of the Desktop App container.
level: component            # context | container | component
container: desktop-app      # required when level: component, absent otherwise
traces_from: [FR-001, FR-004, NFR-002]
traces_to: {}
status: draft
confidence: high
created_at: 2026-08-22
---
```

The body is exactly one fenced ` ```mermaid ` block.

`traces_to.diagrams` therefore holds `DIA-` IDs, consistent with
`traces_to.adr` holding `ADR-` IDs.

**IDs are assigned by the script, not by an agent, and not by the
orchestrator's Stage 4 blocks.** The set size is a function of the model —
`2 + (internal container count)` — and emission order is fixed: `DIA-001` is
the Context view, `DIA-002` the Container view, then one per container in
`draft_diagram_model.containers` order. So the allocation is total,
deterministic and re-derivable from the model alone, which is what keeps a
regeneration from renumbering a set. This is the one place the pipeline's
"only an orchestrator allocates IDs" rule is relaxed, and it is relaxed
because there is no judgment left in the allocation to protect.

Rejected: fixed filenames with no IDs (breaks the one-shape-per-artifact
invariant, and a path is a weaker reference than an ID); frontmatter-free
Mermaid left in `SKIP_DIRNAMES` (drops the ticket's stated `traces_from`
requirement and leaves the diagrams invisible to both validators).

### D4 — Aliases are mechanically derived, and that is what makes checking possible

Mermaid node aliases are computed from artifact IDs by a fixed rule:

| Element | Alias | Example |
|---|---|---|
| Internal component | `cmp_` + digits | `CMP-001` → `cmp_001` |
| External component | `ext_cmp_` + digits | `CMP-010` → `ext_cmp_010` |
| Container | `ctr_` + key | `desktop-app` → `ctr_desktop_app` |
| Actor | `actor_` + key | `owner` → `actor_owner` |
| The system itself | `sys` | — |

Because the rule is total and reversible, the validator can map any node in a
diagram body back to the artifact it claims to depict. That is what lets D6's
consistency check exist without a `depicts` frontmatter field duplicating the
body — and a duplicated field is a drift source, since the two would be
maintained by different edits.

Relation labels carry the interface title and its `IF-` ID.

### D5 — `draft_diagram_model`: the Stage 9.6 hand-off

```yaml
draft_diagram_model:
  system_name: "Tamagotchi Desktop Pet"
  system_description: "..."
  actors:
    - key: owner
      name: "Pet Owner"
      description: "The single local user who cares for the pet."
  containers:
    - key: desktop-app
      name: "Desktop App"
      technology: "Tauri + Rust"       # from design_context.runtime_and_stack
      description: "..."
      components: [CMP-001, CMP-002, CMP-003, CMP-004, CMP-005,
                   CMP-006, CMP-007, CMP-008, CMP-009]
  confidence: high
  reason: "Single-process desktop application; no deployable split."
```

**Invariant the orchestrator enforces before dispatching to the formatter:
every `boundary: internal` component appears in exactly one container's
`components` list.** A component in none is an omission; a component in two is
a contradiction. Both re-dispatch to the `c4-generator`.

External components need no assignment — `boundary: external` already places
them outside every container, and they render as `System_Ext`.

Actors are the only content in this pipeline stage with no upstream artifact
behind them. The generator draws them from use-case and requirement actor
language plus `design_context`, and never invents a role the requirement set
does not name.

A single-container model is a legal and common outcome — the tamagotchi
example is one — and is not a signal that the grouping failed.

### D6 — Emission rules, per level

All three levels use Mermaid's C4 notation (`C4Context` / `C4Container` /
`C4Component`), the notation the ticket names. Every relation is derived from
a `CMP.depends_on → IF.provider` edge; none is invented.

**Context** (`DIA-001`, always exactly one)
- `Person()` per actor
- one `System()` for the system itself
- `System_Ext()` per `boundary: external` component
- relations: depends_on edges that cross the system boundary, plus actor →
  system edges

**Container** (`DIA-002`, always exactly one)
- `Container()` per container, carrying its `technology`
- `System_Ext()` per external component
- relations: depends_on edges whose two endpoints sit in *different*
  containers, or which leave the system entirely

**Component** (`DIA-003`…, one per internal container)
- `Container_Boundary()` wrapping one `Component()` per member component
- an endpoint in another container renders as a `Container()` reference, so a
  cross-container edge terminates somewhere real instead of dangling
- relations: every depends_on edge with at least one endpoint in this
  container

The count rule is therefore `2 + (internal container count)`. There is no
"key container" judgment: the ticket's phrasing invites one, but an
unbounded criterion produces an invisible omission — a container dropped from
the set is recorded nowhere the reader will look.

### D7 — `traces_from` is derived, and the Context view uses the ASR set

For Container and Component views, `traces_from` is the sorted union of the
`traces_from` of every component depicted. Fully derived, no judgment.

The Context view is the exception. Its union is effectively every requirement
in the project, which is honest but carries no information — a trace list that
includes everything distinguishes nothing. It draws instead from
`drivers.md`'s ASR set: the requirements that actually shape system-level
structure, which is what a context diagram depicts.

That places one ordering constraint on the formatter: `drivers.md` must be
written before `generate_c4.py` runs, since the script parses its
`## Architecturally Significant Requirements` section (`- FR-001:
high_impact_function (significance: …)`, one per line). The formatter already
writes the project-level companions alongside the artifact files, so this
constrains the order within Stage 10 rather than adding a step to it.

### D8 — Confidence comes from the model, not per file

Every emitted diagram inherits `draft_diagram_model.confidence`. The
derivation is deterministic, so the only thing that can be wrong in the whole
set is the grouping — and a shaky grouping is a property of the model, not of
one file. A `low` model therefore lands the whole diagram set in `index.yaml`'s
`review_queue`, which is the correct triage signal.

### D9 — Validation is a hard gate, in `validate_design.py`, stdlib only

`diagrams` is removed from `SKIP_DIRNAMES`. Diagram files are then discovered,
schema-validated, and additionally checked:

**Per file**
- the body holds exactly one ` ```mermaid ` block
- its header directive matches the frontmatter `level`
  (`context` → `C4Context`, and so on)
- quotes and parentheses balance
- every `Rel()` endpoint is an alias declared in the same file

**Set level**
- every `cmp###` / `ext_cmp###` alias resolves to a real component in the set,
  with the boundary the prefix claims
- every `IF-` ID cited in a relation label resolves to a real interface
- every internal component appears in exactly one component-level view

No npm, no network, no `mermaid-cli`. The dependency story stays exactly as it
is today: `pyyaml` and `jsonschema` preferred, stdlib fallback available. A
gate whose strength varies with whether `npx` happens to be on the machine is
not a gate.

The diagram↔component consistency check is the one STO-102's description named
("diagram components must match component spec files") and did not ship,
because there were no diagrams to check. It lands here, as an error rather
than a warning: a diagram that contradicts the artifacts is worse than no
diagram, because it will be believed.

### D10 — The content linter needs no changes

Relation labels derive from interface titles. Vague interface titles are
already a `lint_design_content.py` finding. A diagram-prose rule would
re-report the same defect against a second file, which is noise, not coverage.

## Testing

Golden-file fixtures, following the pattern STO-208's lint fixtures
established:

| Fixture | What it pins |
|---|---|
| `c4/multi-container` | cross-container edges render as `Container()` refs |
| `c4/single-container` | the degenerate-but-legal 3-file case |
| `c4/externals` | `System_Ext` rendering and boundary-crossing relations |
| `c4/unassigned-component` | the D5 invariant fails as an error |
| `c4/alias-drift` | a hand-edited `Rel()` endpoint fails the D9 check |

Emission is asserted against committed golden Mermaid, not against a
regex — a golden file is what makes a layout change visible in review.

**End-to-end smoke test.** `generate_c4.py` is run over the shipped tamagotchi
design set (9 internal + 2 external components, single container) and its
output committed, with a note in the example README recording that the
diagrams were generated post-hoc against a set produced before this ticket.
Diagrams are derived, so they cannot contradict the artifacts they are drawn
from. STO-219 regenerates the whole set properly later; this ticket is the
last of its five blockers.

## Out of scope

- **Deployment and code-level C4 views.** The ticket names three levels.
- **Rendering to SVG/PNG.** The artifacts are Markdown; renderers handle
  Mermaid.
- **A `container` field on the component schema.** Container membership is a
  view concern, recorded in `draft_diagram_model`, not a property of the
  component. Adding it would put a second, hand-maintainable copy of the
  grouping in the artifact set.
- **Regenerating the worked examples.** STO-219 owns that, deliberately, and
  it runs once after this ticket rather than per-ticket.
