# Design Assumptions, Dependencies & Open Questions

## Assumptions
- A-1: The owner's reminder preference is persisted in the same local state file as the pet, and CMP-001 owns both. No requirement names a settings store, and CON-002 forecloses remote configuration, so a second persistence element would have been invented rather than derived.
- A-2: Decay continues while the application is running, not only across closures. FR-002 states only the launch-time case, but a pet that decayed only while the app was closed would contradict the system purpose, so CMP-003 applies the same model on a low-frequency timer within NFR-002's idle budget.
- A-3: The OS filesystem is deliberately NOT modelled as an external component, while the OS clock is. NFR-004 requires the commit protocol to be owned by exactly one element, which makes CMP-001 itself the platform port for storage; NFR-001 conversely requires the clock to be injectable so the decay path is testable without real elapsed time, which requires a named provider. If the reviewer prefers consistency over these two ASRs, the correction is to add an external filesystem component and thin CMP-001 accordingly.
- A-4: Death being permanent (Q-2) is assumed to gate care actions, not merely to stop Decay: CMP-003 consults lifecycle state before applying any Stat increase. No requirement states this gate explicitly; it follows from BR-001 plus the Q-2 resolution.
- A-5: Sleep (FR-006) is modelled as a timed process inside CMP-003 rather than as its own component. FR-006 gives it a duration and an interruption rule but no structure that a separate element would carry.
- A-6: The reference decay function is assumed to be pure and parameterised entirely by configuration, so CMP-002's contract can be authored before Q-1 is answered. If the answer to Q-1 turns out to need per-stat state or history, CMP-002's signature changes.
- A-7: Care-action increments, warning thresholds, mood bands, and neglect thresholds are assumed to be configuration read at startup rather than design-time constants, because the requirement set consistently describes them as 'configured' or 'defined'.
- A-8: The Decay model is a pure function of (current Stats, elapsed interval) and needs no history beyond the interval. Q-1 is still open on the curve itself; if it resolves to anything path-dependent, IF-004 gains an input and both of its consumers change.
- A-9: A single clock instance backs IF-001 for every consumer in a session. Stamping the log, the last-saved timestamp, and the neglect timers from one source is what makes NFR-007's entries orderable and NFR-001's tests reproducible; five independently-sampled clocks would satisfy the same frontmatter and none of the guarantees.
- A-10: Diagnostic logging may be lossy on a crash. IF-002 accepts entries without blocking the caller and offers an explicit flush; NFR-007's "0 missing transition entries over 24 hours" is read as a steady-state claim, not a crash-safety claim. If it is meant as the latter, IF-002 must become synchronous and NFR-002's idle budget has to absorb it.
- A-11: The care-reminder preference is stored by CMP-001 as a record separate from the pet state, so that FR-010's quarantine-and-restart recovery does not silently discard the owner's setting. Nothing in the brief states where the preference lives; only that CMP-008 does not hold it.
- A-12: The unseeded window is real and observable. IF-005, IF-006 and IF-007 all report a before-seeding state because CMP-007 sequences the launch and the window exists as a component before it has values to show; if the runtime instead constructs consumers only after seeding, those error modes become unreachable rather than wrong.
- A-13: The capability phrasing "track ... as they change" is read as push (subscription), not polling. NFR-002's <= 1% idle CPU budget and FR-007's one-second bound force it, but the component specialist wrote the capability in observational language that does not by itself name a mechanism.
- A-14: Death being terminal (Q-2) is enforced at the mutation boundary in IF-008 rather than independently by each caller. The alternative — every consumer checking IF-006 first — was rejected because it makes the gate optional in practice.

## Dependencies
- D-1: Depends on the OS notification service being reachable from the Tauri process on Windows for v1. FR-009 must degrade to raising no reminders, rather than failing, wherever it is not.
- D-2: Depends on the target platform providing an atomic rename within the app-data directory. NFR-004's zero-corrupt-loads guarantee rests entirely on that primitive, and CON-003 requires an equivalent on all three platforms.
- D-3: Depends on the system webview exposing an accessibility tree that a screen reader can read on each target platform. NFR-003's WCAG 2.1 AA verification is not achievable from application code alone if the host webview does not surface it.
- D-4: Depends on Q-1 being answered before CMP-002 and CMP-004 can be verified. NFR-001's +/- 1 stat-unit tolerance and FR-008's boundary timings are both measured against values that do not yet exist.
- D-5: Depends on the OS reporting a monotonic-enough wall clock that BR-002's backward-change detection is the exception rather than the routine case; frequent backward adjustments would make Offline-elapsed decay systematically under-apply.
- D-6: The OS notification service (CMP-010) is available on Windows for v1; macOS and Linux equivalents exist but are unverified here, and CON-003 requires IF-012 to be satisfiable on all three without a design change.
- D-7: The OS app-data directory and an atomic file-replace primitive on each target platform. IF-003's commit guarantee is a restatement of that primitive; if any target lacks it, the contract holds but NFR-004's zero-corrupt-loads measure does not.
- D-8: The Tauri process boundary sits between CMP-006 and every component it consumes from, so IF-005, IF-006, IF-007, IF-008 and IF-010 all cross an IPC hop that the other interfaces do not. Transport is deliberately out of scope for these specs, but FR-007's one-second bound and NFR-003's keyboard-response expectations are measured across that hop.
- D-9: OS notification permission is a per-user, per-platform grant outside the application's control, and FR-009 cannot be met without it regardless of the owner's in-app preference.

## Open Questions
- Q-1: What is the exact decay-curve and balance tuning (rates, thresholds, increments)? (owner: product)
- Q-5: BR-001's statement text still asserts that "upon death the pet is reset to a new pet according to the death-handling policy", which the Q-2 resolution taken in the design interview supersedes — death is permanent, one terminal lifecycle path, no reset. BR-001's own rationale already defers that clause to Q-2 and holds the rule at low confidence pending it, so the design resolved a question BR-001 declared open rather than overruling it. The requirement needs amending upstream: strike the reset clause from BR-001's statement and description, record the Q-2 resolution in its rationale, and re-assess its confidence. (owner: product)
